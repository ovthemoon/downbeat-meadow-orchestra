# downbeat_supervisor

Starts the hand tracker and the Unity player, starts them again when they stop, restarts either one when its heartbeat stops (the player's main thread frozen, or the tracker stuck in a camera read that never returns), and restarts the player when its sound clock has been still too long or never came up. Plain Python 3.12, no packages.

```
cd supervisor && ../tracker/.venv/bin/python -m pytest -q        # 116 tests (fake clock and processes, plus a few real child processes)
PYTHONPATH=supervisor tracker/.venv/bin/python -m downbeat_supervisor --config supervisor/configs/mac.json --root builds/mac --var input=replay
```

- **Rules** (`configs/*.json`, the reasons for every number are written in the file under the keys that start with `_`):
  - A stopped process comes back after `restartDelaySec` (3 s).
  - The player writes `heartbeat.txt` from its first frame on, every 5 s (line 1 UTC time, line 2 `audio=starting|ok|stalled|failed`, line 3 `app=loading|running|failed`: loading until Boot has finished, failed once it gave up for any reason, an error in Boot included). The beat older than `heartbeatTimeoutSec` (30 s) restarts it. A read that finds the file empty or unreadable while the player rewrites it is no news: the supervisor judges the newest good beat of this start, so only its age counts.
  - `audio=stalled` or `audio=failed` or `app=failed` for `audioStallRestartSec` (20 s) restarts it (`audio_stalled`, `audio_failed`, `app_failed` in the record). `app=loading` for more than `heartbeatGraceSec` (180 s on Windows) after the start restarts it (`app_not_ready`), and so does `audio=starting` (`audio_not_started`) or no beat at all (`heartbeat_missing`). A running audio clock is not proof that the app is up (a Boot that threw leaves it loading for ever with the clock going), so a start that says `app=loading` is never counted as healthy for the stability reset. An older player without the `app=` line is taken as it was before.
  - The tracker writes its own `tracker-heartbeat.txt` from its frame loop every 2 s, with or without a camera (the loop that opens the camera again is alive); the process setting `heartbeatTimeoutSec` (45 s) restarts a tracker whose beats stop, which is a camera `read()` or `open()` that does not return (Media Foundation after a USB unplug).
  - **The player ends itself** when its main thread has run no frame for `--stall-exit-sec` seconds (20 by default, from the moment it says `app=running`), or when its log hook receives a line that says the graphics device is lost. It first writes one line with the reason to its Player.log (`[selfexit] reason=...`) and to `exit-reasons.txt` next to `heartbeat.txt` (one line per exit, kept across restarts), then ends with exit code **71** (graphics device lost) or **72** (main thread stalled). The supervisor needs nothing for it: any exit is an `exit` row with `code=71` or `code=72`, followed by the restart after `restartDelaySec`, and it counts as a start that ended before it was stable (the rests below). 20 s plus the exit's own steps (23 s at most) is earlier than the earliest `heartbeat_stale` of a frozen player (30 s minus the 5 s beat = 25 s), so the app's own reason is the one on record; `StallExitSettingTests` reads `heartbeatTimeoutSec` from `configs/windows.json` and keeps the two apart, so lowering it there needs a look at that test.
  - More than 5 restarts in 10 minutes rest 60 s (`backoff`).
  - **Rests that grow.** A start is *stable* when it was healthy (player: a beat that is fresh with the sound `ok`; a process without a heartbeat file: alive) for `stableAfterSec` (120 s) without a break. When `unstableRuns` (3) starts in a row ended before they were stable, whatever the reason (an exit, a kill, a program that cannot be started), the rest after each further one doubles: 60, 120, 240, 480 and then `maxRestSec` (600 s), with a `backoff_escalated` row that says how many and why; a stable start puts everything back (`recovered`). It never gives up: when the sound device comes back the next try (at most 10 minutes later) works. Why 3, 120 s and 600 s is in `configs/windows.json`.
- **Record**: `logs/supervisor-yyyyMMdd.csv` with `timestamp_utc,process,event,detail` (an `exit` row with `code=71` or `code=72` is the player ending itself: the reason is in `logs/exit-reasons.txt`); each child's output in `logs/<name>.out.txt`, which only catches stray stdout and stderr (the tracker's own log, `tracker-supervised.log`, is rotated separately by the tracker: 5 MB, 3 older files). The output file is moved to `.out.1.txt` ... `.out.3.txt` when it is over 5 MB **at the start of every process, on every platform** (before the child gets the file). **Mac and Linux** also check it once a minute while the child runs: the file is copied to `.out.1.txt` and emptied in place, which is safe there because the child's writes are O_APPEND and land at the new end; so at most 20 MB per process. **Windows does not trim a running child's file**: the child holds a duplicated handle that shares the file pointer with the supervisor, so after emptying the file its next write would land at the old offset, leave a hole of zero bytes and lose the log. On Windows the file therefore grows for as long as one run lasts and is moved away at the next start (a restart for any reason, or the next launch of the supervisor). Worst case: the size at the start (5 MB at most) plus everything the child writes to stdout and stderr in that one run, and a moved-away generation can be that large, so the 20 MB figure holds on Mac and Linux but not on Windows. By arithmetic, not by measurement: a child that writes 100 bytes a second (an error line in a loop) adds about 8.6 MB a day, 1 kB a second about 86 MB a day. To free the space on a Windows machine, stop the supervisor and delete or move the file.
- **Configuration**: `{root}` (the folder of the player), the `vars` of the file and `--var name=value`; a process can have `"when": {"var": "input", "equals": "hand"}` and a word of a command can have the same, so the tracker is left out with `--var input=mouse`. A conditional entry of a command is `{"word": "--soak", "when": {...}}` or a group `{"words": ["--quality", "{quality}"], "when": {...}}`; `when` compares exactly, so `--var quality=High` or `Low` passes `--quality High|Low` to the player and any other value (or none) passes nothing.
- **What it cannot see**: a frozen picture that still beats, a black or garbled frame, the record on the wrong monitor. The heartbeat is written by the player's main thread, so a frozen main thread is seen; the CSV health log is not a freeze detector. A tracker whose camera keeps returning the same picture (a frozen stream) or garbage still beats: only a read that does not return is seen, not what the frames contain; hands that are not found in a good picture are not a fault either. A heartbeat the app had to write somewhere else than the folder the supervisor reads (the app folder is not writable) looks like a dead app: the app logs an error for it, and the supervisor restarts it again and again with the growing rests.
- Windows: `tools/windows/run-supervised.ps1` (and `install-autostart.ps1`, a shortcut in the user's Startup folder); Mac: `ops/mac/run-demo.command`.
